# Technical Report: API Performance Optimization (CTS Backend)

## 1. Executive Summary
This document outlines the investigation and resolution of a critical performance bottleneck in the CTS Backend API. The system was experiencing response times of **3 to 4 seconds** on primary endpoints, leading to **502 Gateway Timeouts** and high vulnerability to service degradation under light load.

The root cause was identified as a classic **N+1 Query Problem** exacerbated by **Network Latency** between the API server (Render) and the database (Supabase).

## 2. The Problem: "The N+1 Death Loop"

### Technical Root Cause
The original code followed an iterative data retrieval pattern. To display a list of 10 elections (Positions), the code performed the following operations:
1.  Fetch all Positions (**1 query**).
2.  Loop through each Position to count total votes (**10 queries**).
3.  Loop through each Position to fetch its Candidates (**10 queries**).
4.  For every Candidate found (e.g., 3 per position), fetch their specific vote count and user details (**30+30 queries**).

In a typical scenario, a single request was triggering **70 to 100 separate database queries**.

### The "Internet Tax" (Latency)
Because the database is hosted on Supabase, every single query incurs a **Round-Trip Time (RTT)** (approx. 70ms - 150ms depending on region).
*   **70 queries × 80ms = 5.6 seconds** of idle waiting.
The CPU was doing almost no work; it was simply waiting for the network signal to travel back and forth 70 times.

## 3. The Solution: Set-Based Operations

The codebase was refactored to move from "iterative" logic to "set-based" logic using Laravel Eloquent's advanced features.

### Key Changes
1.  **Eager Loading (`with`)**: Instead of fetching candidates one by one inside a loop, we now tell the database to "Join" or pre-fetch all candidates and their associated users in a single operation.
2.  **Aggregate Counting (`withCount`)**: We replaced manual `count()` queries inside loops with sub-queries. The database now calculates the vote counts *while* it is fetching the positions.
3.  **Relationship Mapping**: Added the missing `votes()` relationship to the `Candidate` model to enable these aggregate optimizations.

### Results
*   **Old Query Count**: ~80 queries per request.
*   **New Query Count**: **3 queries** per request.
*   **Theoretical Latency Reduction**: From **4000ms+** to **~200ms** (a 95% improvement).

## 4. Logic & Stability Fixes
During the refactoring, several critical bugs were identified and resolved:
*   **Vote Detection Inconsistency**: The system was checking for user votes using a SHA256 hash in some places and a plain Email hash in others. This made the "already voted" detection unreliable. It is now unified to use the Email-based `hash_session`.
*   **SQL Error Prevention**: The `checkVote` endpoint was querying a non-existent `user_id` column in the `votes` table. This was corrected to use the `hash_session` column.
*   **Null-Safety**: Added protection against orphaned candidate profiles (candidates without a valid user link) to prevent 500 errors.

## 5. Infrastructure Recommendations
To achieve sub-100ms performance, the following infrastructure steps are recommended:
1.  **Connection Pooling**: Use the Supabase Transaction Pooler (Port 6543) instead of the direct Postgres port to avoid the "SSL Handshake Tax" on every request.
2.  **Enable Redis Cache**: Ensure the Render environment has `CACHE_STORE=redis` and a valid Redis URL. This will make subsequent requests instantaneous.
3.  **Database Indexing**: Add a database index on the `candidate_id` and `hash_session` columns of the `votes` table to maintain speed as the volume of votes grows into the thousands.
